Chapter 1

Where things stand

The branch named dev is the production system today. The WeBuddhist app talks to the EC2 instance that dev deploys to. The goal is to have two copies: dev for testing and main for real users. You build and test the main copy first, then point the app at it.

The repo also has about 30 feature branches. They do not trigger deploys.

Chapter 2

System map

The backend runs as one process group on one EC2 instance. systemd keeps gunicorn running, and gunicorn runs four copies of the FastAPI app. On startup each copy connects to three AWS-side services. It does not start if OPENSEARCH_ENDPOINT is missing (main.py:71).

Chapter 3

How a request moves

Pick a request and press Play, or step through it. Every request first checks the API key against Neo4j, unless ENVIRONMENT=dev. Search indexing always runs after the response has been sent, as a FastAPI background task. There is no queue and no retry, so a failed index update shows up only in the logs.

    Chapter 4

    Data model

    Neo4j holds everything except the text itself and the audio. A Work is the abstract work. A Text is one language version of it. An Edition is a concrete witness of a Text, such as a particular printed pecha. Its characters live in S3. Every annotation points at character ranges in that S3 file through Span nodes.

    About 70 APOC triggers check the graph's shape when a transaction commits, for example "a diplomatic edition must have exactly one pagination". A broken rule comes back from the API as 422, and a uniqueness violation as 409 (main.py:39-60).

    Chapter 5

    Text and spans

    A span is a half-open range [start, end) of Unicode code points in the edition's base text. When someone edits the text with PATCH /v2/editions/{id}/content, one Neo4j transaction moves every affected span first. Then the S3 file is rewritten. If the S3 write fails, the API reverses the span change. The two stores are not updated atomically.

    Segments and pages are continuous: they tile the text, so an insert at their end makes them grow. Notes and marks are annotations: an insert at their end leaves them alone. The example below shows this with four Tibetan syllables.

    Segmentation (continuous)
    Yigchung mark (annotation)

    The rules come from docs/text-operations-spec.md (insert, delete and replace tables) and are implemented in database/span_database.py:250-358. One exception: an insert at offset 0 expands the first span instead of shifting it.

    Chapter 7

    Deploy pipeline

    One workflow file, .github/workflows/deploy.yml, handles both environments. The branch name picks the GitHub environment, and that environment supplies the role, the instance id and every setting. There are no SSH keys and no stored AWS keys. GitHub proves its identity to AWS through OIDC, and AWS Systems Manager runs the script on the instance.

    1. Push

      A push to dev or main, or a manual run (workflow_dispatch). Other branches do nothing.

    2. Run the tests

      Ubuntu runner with Python 3.14 runs pytest tests/. Testcontainers start neo4j:2026.07.1 with APOC and opensearch:3.5.0. This takes about 4 minutes, and deploy waits for it.

    3. Choose the environment

      Environment dev. Its variables and secrets become available to the job.

    4. Assume the AWS role

      configure-aws-credentials trades the GitHub OIDC token for vars.AWS_ROLE in vars.AWS_REGION.

    5. Write the deploy script

      A bash script with a .env heredoc. Values are filled in from the dev environment.

    6. Send it to the instance

      aws ssm send-command runs AWS-RunShellScript on vars.EC2_INSTANCE_ID and waits. If it fails, the job prints the instance's output.

    7. Update the code

      In /opt/openpecha-backend: git fetch, checkout and pull dev, then rewrite .env.

    8. Install and restart

      Check for python3.14, then reuse or recreate .venv, run pip install -r requirements.txt, chown, and systemctl restart openpecha-api. About 20 seconds.

    What runs on the instance (from deploy.yml)

    Chapter 10

    Cutover

    Because the two branches share no history, main is moved, not merged. Save the old Firebase code under a new branch name. Then point main at the commit dev runs today. After that, the normal flow is a pull request from dev into main.

    1. Finish chapter 9 up to the deploy step. Add yourself as a required reviewer on the prod environment so no deploy goes out without your approval.
    2. Move main, approve the run, and check GET /__/health and /docs on the prod host.
    3. Point a test build of the WeBuddhist app at prod. Click through reading, search, audio and one write.
    4. Pause writes on dev, or re-copy the data (Neo4j, S3, reindex) right before the switch, so prod has everything.
    5. Release the app with the prod URL, plus the API key if prod enforces keys.
    6. Keep dev unchanged. To roll back, point the app at dev again. After the switch, dev's data starts to drift; it is test data from then on.
    Chapter 11

    Look up in AWS

    The repository does not say how these were set up for dev. Look at the dev resources and copy their settings.

    HTTPS front door

    gunicorn listens on 0.0.0.0:8000 over plain HTTP. Something in front of it terminates TLS and owns the API's domain name.

    EC2 → Load Balancers, or nginx on the instance, plus Route 53 and ACM
    Where Neo4j runs

    Neo4j Aura or a self-hosted instance. This decides how you copy data (snapshot or neo4j-admin dump) and where APOC is configured.

    GitHub env dev → NEO4J_URI
    Instance role and security groups

    The role on the dev instance grants S3 and SSM. Its security group lets traffic in from the front door and out to OpenSearch.

    EC2 → dev instance → Security, IAM role
    OpenSearch access policy

    The app connects without signing (auth_mode=none), so the dev domain must allow its VPC. Copy the policy exactly, or switch prod to aws auth.

    OpenSearch → os-dev → Security configuration
    Deploy role permissions

    Copy the dev role's trust policy, but limit it to environment:prod, and point its permissions at the prod instance.

    IAM → Roles → vars.AWS_ROLE from the dev environment
    Repo access on the instance

    The deploy runs git fetch as root. If the repo is private, root needs a deploy key or token on the instance.

    dev instance → /root/.ssh, git remote -v

    Sharp edges found while reading the code

    • Overlapping deploys. On 2026-09-28 a deploy that was still running finished after a rollback and put the wrong commit back. A concurrency group in deploy.yml would make deploys queue.
    • Creating an edition writes S3 first. If the Neo4j step then fails, the text file stays in S3 with nothing pointing to it.
    • Deleting an edition leaves its S3 files. DELETE /v2/editions/{id} removes the graph nodes and search chunks, but not the base text or audio.
    • Constraints and triggers are not applied on startup. A new database needs neo4j_constraints.cypher and scripts.install_neo4j_triggers run by hand.
    • The README is out of date. It says deploys happen on main, which was true for Firebase. Today they happen on dev.
